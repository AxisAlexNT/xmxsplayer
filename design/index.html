xmxsplayer — design reference

Static mockups of the target interface. They are the visual specification: layout, colours, sizes, states and wording. The staves, piano rolls and waveforms are drawn by a small demo script; everything else is plain markup and CSS that the Vue components should reproduce.

Main windowTransport bar, left panel, tracks with staff / piano-roll / audio lanes, keyboard strip. Open at 1920×1080. Left panel sectionsController schematic, signal flow, scenes, registers, patch, clips, devices, soundfonts, sources, script, log. Dialogs and popoversBinding editor, zone and follow popovers, clip editor, instrument picker, cue editor, settings, learn wizard, banners, toasts. States and tokensFollow views, staff themes, transport and track states, pad LED states, colours, type, buttons.

Rules the mockups follow

  1. Dark, low-glare, colour means something. Greys carry structure; colour is reserved for track identity and state (green playing/AUTO, orange LIVE, amber waiting/modified, red record/error, blue focus/playhead).
  2. Touch and pen first. Every interactive target is at least 40 px in one dimension; nothing works only on hover; drag handles are at least 12 px.
  3. Bars line up. All lanes share one horizontal time axis. Each page starts with a lead-in gutter (clef and key on staves, key legend on piano rolls); after it, a bar line is at the same x in every lane.
  4. One playhead. A single accent line crosses all lanes. In page view it moves; in center view it stays at 50 %.
  5. Screen and hardware agree. A pad, clip tile and KeyLab LED use the same colour and the same four states: off, idle, on, queued.
  6. Popovers apply immediately; dialogs confirm. Small edits (zone, binding, patch connection, register) are popovers without OK. Larger objects (clip, cue, instrument, settings) are dialogs with one primary button.
  7. Mono for numbers. Positions, tempo, key ranges, bank:program, latency and file sizes use the mono font with tabular figures so they do not jitter.
